# TripIt v2 `CarObject`

This is reverse-engineered documentation for the new v2 web application shape. It is not an official TripIt API contract.

## Scope and evidence

The primary source is `www.tripit.com.har` in this directory. The capture contains one successful authenticated request to the object-inclusive trip endpoint (the trip and reservation identifiers are intentionally omitted here):

```text
GET /api/v2/get/trip/uuid/{trip_uuid}/include_objects/true?exclude_types=weather&should_get_new_seat_tracker_subscriptions=true
```

The response has a root `CarObject` **object**. It has no `Segment`, `Driver`, address, agency, booking, or supplier subobjects in this sample. The same response has `AirObject` and `LodgingObject` arrays, so a consumer should not assume every `*Object` root key has the same wire cardinality.

The bundled assets in the HAR provide the second source of evidence:

- `index-C6qCNcMY.js`: model classes, serializers, API helpers, and the reservation-type map.
- `ActivityObject-BGf0RlZP.js`: common reservation and agency model classes.
- `Address-Hl9pc1FK.js`: common address model.
- `BaseSegment-DQFXsffw.js`: common segment base class.
- `view-primary-PQx7yYZa.js`: car page fields and display logic.
- `more-details-6dKrRbhO.js` and `en-US-BL_4hUBr.js`: secondary sections and UI labels.
- `TripItemTypes-CeicT-Cc.js`: car route names and `CarObject`/type-code mapping.

The HAR is one point-in-time capture with one car. “Not observed” below means only “not present in this capture”; it does not prove that the field is rejected or never returned. The wire response uses XML-shaped names and represents all observed scalar values as strings, including boolean-looking values and numeric-looking IDs.

## Wire location, cardinality, and frontend normalization

At the response root:

```text
response.CarObject
```

In this HAR, `CarObject` is a singleton object. The web client passes it through a helper that converts an object to a one-element array (and leaves arrays as arrays) before deserializing each item. Therefore an API client should tolerate either a singleton object or an array at this boundary, while treating singleton-object cardinality as the only shape directly demonstrated here.

The frontend maps the object to reservation type code `C` and calls the resulting model `CarObject`. Its model has a `travelers` array, but the wire key for that array is `Driver` (not `Traveler`). Its `segments` property is also a frontend construct, described below; this car serializer does not deserialize a wire `Segment` collection.

## Frontend-only `segments`

For a car reservation, `ql.deserialize` does not read a wire `Segment` array. It creates exactly two `CarSegment` instances from the whole car object:

```text
segments[0] = CarSegment with isPickup = true
segments[1] = CarSegment with isPickup = false
```

Each synthetic segment inherits the source `uuid` into the common segment model. The source class sets `segmentType` to the car type code `C`; this is a model value, not an observed wire key. `isFirstSegment()` is true for pickup and false for drop-off. A segment key is derived as `{uuid}-pickup` or `{uuid}-dropoff` by the frontend.

This explains why the car UI can render a pickup or drop-off page even though the captured `CarObject` contains only reservation-level fields and two reservation-level date-time objects. It does not prove that the public API will always omit raw segments for every car response.

## Endpoint and UI clues

### Captured request and code-derived API paths

- The captured request is the object-inclusive trip fetch shown in the scope section. Its query explicitly excludes weather and requests new seat-tracker subscriptions.
- The bundled API helper builds the trip fetch from `v2/get/trip/uuid/{tripUuid}/include_objects/true`, adding `exclude_types=weather` and `should_get_new_seat_tracker_subscriptions=true` in this flow.
- The same bundle contains generic helpers for `v2/get/{type}/uuid/{uuid}`, `v2/create`, `v2/replacePlan/{type}/uuid/{uuid}`, `v2/delete/{type}/uuid/{uuid}`, and `v2/delete/segment/uuid/{uuid}`. Those are code clues only; no car create, update, or delete request is present in this HAR.

### Car page routes and display behavior

The route table identifies car reservations with type code `C`, object key `CarObject`, and the following route templates (identifiers are placeholders):

- `/trips/{trip_uuid}/car-rental/create`
- `/trips/{trip_uuid}/car-rental/{segment_uuid}`
- `/trips/{trip_uuid}/car-rental/{segment_uuid}/edit`
- `/unfiled/car-rental/{reservation_uuid}`
- `/unfiled/car-rental/{reservation_uuid}/edit`

The captured HTML navigation request is the car-rental view with an `is_pickup=true` query. The car view uses that query to choose pickup versus drop-off location fields and labels.

The loaded car view exposes the following source-backed UI fields and labels:

- Primary: pickup/drop-off location, location phone, hours of operation, duration, and total cost.
- Car Rental Info: car type, mileage charges, and car details.
- More details: Drivers, Booking Info, and Travel Agency Info.
- Edit labels/placeholders also name pickup and drop-off date/time, confirmation, rental agency, website, email, phone, pickup/drop-off location, car type, mileage charges, and car details.

The UI evidence supports the field names and display intent above, but it does not establish which fields are required by the server or what validation rules the API applies.

## Coverage and uncertainties

Covered: all keys in the captured `CarObject`; all car-specific fields declared by the inspected serializer; common reservation, address, traveler/driver, agency, document, and date-time mappings used by that serializer; singleton normalization; synthetic segment behavior; and car-specific endpoint/route/UI clues in the HAR.

Uncertain: API requiredness; whether every response uses singleton `CarObject` versus an array; exact timestamp unit for `last_modified`; exact semantics and accepted formats for IDs, costs, rates, confirmation values, locations, and booleans; whether the three observed extra keys are stable across clients; and whether raw `Segment` or additional undocumented fields appear for other car records.
